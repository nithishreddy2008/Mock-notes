SQL Aggregation & Grouping Execution Lifecycle

Tuple Filtering (WHERE), Partitioning (GROUP BY), Aggregate Computation & Group Filtering (HAVING)

WHERE: Row Filtering

Filters base rows before grouping. Aggregate functions strictly prohibited.

EmpDeptSalary
E1IT60000
E2HR45000
E3IT75000
E4HR25000
E5ITNULL

Predicate WHERE Salary >= 40000 discards E4. E5 passes if IS NULL or unchecked.

→
2
GROUP BY: Partitioning

Partitions surviving tuples into buckets by Dept. Multiple NULLs form one group.

Dept = 'IT' (3 rows)
E1 (60000), E3 (75000), E5 (NULL)
Dept = 'HR' (1 row)
E2 (45000)

Rule: Every non-aggregate column in SELECT must appear in GROUP BY!

→
3
HAVING: Group Filter

Calculates aggregates per group, then filters groups with predicate.

Group: 'IT'
COUNT(*) = 3, COUNT(Salary) = 2
SUM(Salary) = 135000, AVG = 67500
✓ Passes HAVING COUNT(*) > 1
Group: 'HR'
COUNT(*) = 1, AVG = 45000
✗ Dropped by HAVING COUNT(*) > 1
NULL INVARIANT The Golden Invariant of Aggregate Functions & NULLs
  • COUNT(*) Counts Rows: Evaluates total row count of the partition, including rows where attributes are NULL.
  • All Other Aggregates Ignore NULL: COUNT(column), SUM(column), AVG(column), MIN(column), MAX(column) strictly ignore NULL values!
  • AVG Calculation Trap: AVG(Salary) divides by COUNT(Salary), *not* by COUNT(*)! If 3 employees have salaries 60000, 75000, NULL, AVG = 135000 / 2 = 67500 (not 45000).
WHERE vs HAVING Critical Architectural Distinction
  • WHERE Clause: Evaluated at Stage 2. Operates on individual rows *before* aggregation. Cannot contain aggregate functions.
  • HAVING Clause: Evaluated at Stage 4. Operates on summary group partitions *after* aggregation. Can contain aggregate functions (HAVING AVG(Salary) > 50000).
  • Optimization: Always filter individual rows using WHERE before grouping to minimize group computation overhead!
